# Playable 404: pong against the headline

Date: 2026-08-01
Status: approved, not yet implemented

## What this is

The 404 page becomes a playable pong board. The word `404` is drawn as a grid of
bricks traced from the site's own Orbitron headline, a ball knocks the bricks
out, and the visitor drives the bottom paddle. Clearing every brick swaps the
line under the headline from `BREAK IT` to `NOW GO BUILD`.

It replaces the current `GlitchField` treatment on this page only. `GlitchField`
stays in use on the homepage hero and is not touched.

## Why

A 404 is a dead end. This one hands the visitor something to do, and the thing
they do is destroy a page that was never built, which is the company's whole
argument in one gesture. The payoff line is the instruction.

## Origin and what survives from it

The idea came from a dropped-in `PromptingIsAllYouNeed` component. Almost none
of it survives. Discarded: its hand-drawn `PIXEL_MAP` bitmap font (which has no
digits and cannot spell `404`), its hardcoded `#FFFFFF` / `#000000` / `#333333`
palette, its opaque background fill, its four-AI-paddle no-player model, its
`fixed inset-0` positioning, its unconditional `requestAnimationFrame` loop, and
its missing cleanup. What survives conceptually: bricks, four paddles, a
bouncing ball.

## Component boundary

`PixelPong` owns everything that has to stay in sync between the DOM and the
canvas: the `<h1>`, the canvas, and the two-state line. It exposes no props
beyond `className`. The win state never leaves the component.

`not-found.tsx` stays a server component and composes:

```
main (grid rows [auto_1fr_auto], min-h-100svh, isolate)
  header    MaskThemeToggle
  PixelPong (client)          relative, fills the 1fr row
    canvas    absolute inset-0, z-0, the board
    div       relative z-10, pointer-events-none, centred
      h1        "404", Orbitron display, laid out, traced by the canvas
      p         BREAK IT / NOW GO BUILD
  Link "/"  AlgobicLockup + BACK TO START
  footer    SITE.tagline
```

The canvas fills `PixelPong`'s wrapper, so the four paddles sit on the wrapper's
edges rather than the viewport's. The header and footer stay clear of play.

Stacking and hit-testing: the canvas is `z-0` and is the only element that takes
pointer events inside the wrapper. The h1 and the line sit at `z-10` with
`pointer-events-none`, so dragging across the headline still drives the paddle.
The `BACK TO START` link is a sibling of `PixelPong`, not inside it, so it keeps
its own hit area and focus behaviour.

`metadata` keeps `robots: { index: false, follow: true }` and the existing
title and description.

## The type pipeline

The bricks are traced from the real headline, not from a lookalike bitmap.

1. Wait for `document.fonts.ready`. Sampling before this traces the fallback
   face and produces bricks shaped like Arial.
2. Measure the `<h1>` with `getBoundingClientRect()`.
3. Read `getComputedStyle(h1)` and copy its `font` shorthand straight onto the
   offscreen `ctx.font`, and its `letterSpacing` onto `ctx.letterSpacing`. The
   CSS is the single source of truth for the type; the canvas only traces it.
   Nothing about the size, weight, family or tracking is duplicated in JS.
4. Draw the text into an offscreen canvas the size of the h1's box.
5. Walk a grid over that box. A cell whose sampled alpha exceeds 128 becomes a
   brick.

Grid resolution: `cell = max(4, round(boxHeight / 14))`. Fourteen rows of cells
across the cap height is enough for Orbitron's squared-off `4` and `0` to stay
recognisable, and coarse enough to read as bricks rather than as anti-aliasing.
Each brick paints at `cell - gap` where `gap = max(1, round(cell * 0.12))`.

### Progressive enhancement

The `<h1>` renders at full opacity by default. The component sets
`color: transparent` on it only after a sample has succeeded and produced at
least one brick. So:

- no JS, no canvas, or a font that never loaded: a visible Orbitron `404`
- sampling succeeded: bricks, and the h1 is a transparent but real, selectable,
  screen-reader-visible, crawlable `<h1>404</h1>`

A failure here can only leave the headline readable, never invisible. This
mirrors the rule already stated in `globals.css`: the default state is finished
content.

## Palette

Read from the CSS custom properties with the same `readPalette()` pattern
`glitch-field.tsx` uses, and re-read on a `MutationObserver` watching
`documentElement`'s class list so the theme toggle repaints the board.

| Element | Token | Reason |
| --- | --- | --- |
| canvas background | none, transparent | the page's `--background` shows through, so the view-transition theme wipe passes over the board instead of being blocked by an opaque fill |
| intact brick | `--foreground` | it is the headline |
| smashed brick | `--line` | destroyed, still faintly present |
| ball | `--accent-ink` | 6.26:1 light, 6.53:1 dark. `--accent` measures 2.44:1 on paper and would be an invisible ball |
| player paddle | `--accent-ink` | the only thing the visitor operates |
| three AI paddles | `--muted` | machinery, not controls |

## Play

Bottom paddle is the player's. Three AI paddles on the other edges track the
ball with a lerp of 0.06, detuned from the reference's 0.1 so the player's
paddle is the one that decides anything.

Input, all three driving the same clamped target x:

- pointer move over the canvas
- touch drag, with `touch-action: none` on the canvas
- Left and Right arrows. The canvas takes `tabIndex={0}` and an `aria-label`,
  so it picks up the site's existing `:focus-visible` ring for free.

All four walls reflect the ball. There are no lives and no game over. Stranding
a frustrated visitor on an error page with a fail state is a worse 404 than the
one this replaces.

Player paddle deflection: on contact, `dx` is nudged by
`(ballCenterX - paddleCenterX) / halfLength * SPIN` and the velocity is
renormalised to constant speed. Without it the paddle is a wall and there is no
skill in the game.

## Collision

The ball is a square, side `cell * 1.5`, because the site's visual vocabulary is
horizontal bars and one 16 degree slash and contains no circles anywhere else. A
square ball is the same shape as the brick it destroys.

Brick collision is axis-aligned box overlap, resolved on the axis of **greater
penetration depth**, not on the reference's center-distance comparison.

Hits are collected for the whole frame and each axis is flipped at most once per
frame. The reference flips `dx` or `dy` once per brick hit inside the loop, so a
ball entering a corner and clearing three bricks in one frame flips the same
axis three times and the reflection cancels itself out.

## The two-state line

`BREAK IT` before the board is cleared, `NOW GO BUILD` after. Real DOM text in
the existing eyebrow style, not bricks: selectable, announced, and it never
needs a re-sample. The wrapper carries `aria-live="polite"`.

Both spans render; CSS decides which is visible. This avoids a hydration
mismatch and the one-frame flash of the wrong line that a
`useMediaQuery`-at-render approach would produce, since the server has no way to
know the reader's motion preference.

```css
/* Play state is the default; the cleared state and reduced motion both show
   the payoff instead. */
.pong-line [data-state="done"] { display: none; }
.pong-line[data-cleared="true"] [data-state="play"] { display: none; }
.pong-line[data-cleared="true"] [data-state="done"] { display: inline; }

@media (prefers-reduced-motion: reduce) {
  .pong-line [data-state="play"] { display: none; }
  .pong-line [data-state="done"] { display: inline; }
}
```

## Reduced motion

Gated on `prefersReducedMotion()` from `motion-provider.tsx`, which the codebase
declares as the single source of truth. Not `matchMedia` directly.

When it is set: sample, paint one frame, return. No `requestAnimationFrame` is
ever scheduled, no pointer or key listeners are attached, and the ball and
paddles are drawn in their starting positions. The line reads `NOW GO BUILD`
straight away, because inviting somebody to break something that cannot move is
a dead link written as copy.

A `change` listener on the media query rebuilds the loop if the preference is
turned off mid-session, matching what `GlitchField` already does.

## Lifecycle and cost

- Device pixel ratio capped at 2, same `MAX_DPR` as `glitch-field.tsx`.
- `ResizeObserver` on the wrapper re-measures the h1, re-samples, and resets the
  board. Guarded against the observer's initial delivery reseeding a board that
  was just built, the same guard `GlitchField` carries.
- `visibilitychange` cancels the frame on a hidden tab and restarts it on
  return.
- Brick count at a desktop headline is in the low hundreds, so a naive per-frame
  loop over all bricks is fine. No spatial index.
- Every listener, observer and animation frame is torn down in the effect's
  cleanup. The reference component leaked its `requestAnimationFrame` loop
  forever; that is the single worst thing in it.

## Accessibility

- A real `<h1>404</h1>` in the DOM at all times.
- The line is real text in a polite live region.
- `BACK TO START` is a real `next/link`, always visible, never gated behind
  winning.
- The canvas is focusable, labelled, and keyboard-playable. Anyone who cannot
  play it loses nothing: every piece of content and the only navigation on the
  page live in the DOM, not on the canvas.
- Focus ring comes from the global `:focus-visible` rule, which already clears
  3:1 against both `--background` and `--surface` in both themes.

## Verification

The repo has no test framework and this change does not justify introducing
one. Verification is:

1. `npm run lint` clean.
2. `npm run build` clean.
3. Load `/does-not-exist` and confirm, by hand:
   - bricks spell `404` in Orbitron, matching the h1's metrics
   - the ball clears bricks and the line swaps on the last one
   - mouse, touch and arrow keys all move the bottom paddle
   - the theme toggle repaints the board without reloading
   - with reduced motion forced on, the board is a still image, the line reads
     `NOW GO BUILD`, and no frames are scheduled
   - with JS disabled, a visible Orbitron `404` and a working link
   - `Ctrl+Shift+P` in devtools, "Show rendering", no layout thrash on pointer
     move
